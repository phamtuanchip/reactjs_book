Deployment & CI/CD

Viết code xong chỉ là nửa công việc — deploy lên production mới là đích đến thực sự. Chương này hướng dẫn deploy React/Next.js lên Vercel, Netlify, và thiết lập CI/CD với GitHub Actions.

24.1 Build và chuẩn bị Production

# Vite React — build production
npm run build
# Output: dist/ folder
# dist/index.html
# dist/assets/index-[hash].js     ← minified, tree-shaken
# dist/assets/index-[hash].css

# Next.js — build production
npm run build
# Output: .next/ folder
# + standalone build (for Docker)

# Kiểm tra build locally
npm run preview  # Vite: preview production build
npx serve dist   # Hoặc dùng serve package

# Phân tích bundle size
npm install -D rollup-plugin-visualizer
# Trong vite.config.ts:
import { visualizer } from 'rollup-plugin-visualizer';
plugins: [react(), visualizer({ open: true })]
# Sau khi build: dist/stats.html → xem bundle treemap

24.2 Environment Variables

# .env files (Vite)
.env                  # Mọi môi trường
.env.development      # Chỉ development (npm run dev)
.env.production       # Chỉ production (npm run build)
.env.local            # Override local (gitignored)

# Vite: phải có prefix VITE_ để expose ra client
VITE_API_URL=https://api.example.com
VITE_APP_NAME=My App
DATABASE_URL=postgres://...  # Không có VITE_ → chỉ server-side

# Trong code (Vite)
const apiUrl = import.meta.env.VITE_API_URL;
const isProduction = import.meta.env.PROD;

# Next.js
NEXT_PUBLIC_API_URL=...     # NEXT_PUBLIC_ → expose ra client
DATABASE_URL=...             # Server-only (không ra browser)

# Trong code (Next.js)
const apiUrl = process.env.NEXT_PUBLIC_API_URL;
// Server-only (API routes, Server Components):
const dbUrl = process.env.DATABASE_URL;

# QUAN TRỌNG: .env không commit vào git!
# .gitignore:
.env
.env.local
.env.*.local
# Tạo .env.example với placeholder values (commit để team biết)

24.3 Deploy lên Vercel

# Vercel — tốt nhất cho Next.js (cùng team)
# Cách 1: Vercel CLI
npm install -g vercel
vercel login
vercel           # Deploy preview
vercel --prod    # Deploy production

# Cách 2: GitHub integration (khuyến nghị)
# 1. Push code lên GitHub
# 2. vercel.com → Import Project → chọn repo
# 3. Mỗi push vào main → tự động deploy production
# 4. Mỗi PR → tự động deploy preview URL

# vercel.json — config tùy chỉnh
{
  "buildCommand": "npm run build",
  "outputDirectory": "dist",      # Vite, nếu không phải Next.js
  "installCommand": "npm install",
  "framework": "nextjs",          # hoặc "vite"
  "env": {
    "DATABASE_URL": "@database-url"  # Reference từ Vercel secrets
  },
  "routes": [
    {
      "src": "/(.*)",
      "dest": "/index.html"       # SPA fallback cho client-side routing
    }
  ]
}

# Thêm environment variables:
# Vercel Dashboard → Project → Settings → Environment Variables
# Hoặc: vercel env add DATABASE_URL production

24.4 CI/CD với GitHub Actions

# .github/workflows/ci.yml
name: CI/CD Pipeline

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'

      - name: Install dependencies
        run: npm ci  # Nhanh hơn npm install, dùng package-lock.json

      - name: TypeScript check
        run: npm run type-check

      - name: Lint
        run: npm run lint

      - name: Run tests
        run: npm run test -- --run  # Vitest one-time run (không watch)
        env:
          DATABASE_URL: ${{ secrets.DATABASE_URL_TEST }}

      - name: Build
        run: npm run build
        env:
          NEXT_PUBLIC_API_URL: ${{ secrets.NEXT_PUBLIC_API_URL }}

  deploy-preview:
    needs: test
    if: github.event_name == 'pull_request'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Deploy to Vercel Preview
        run: vercel --token ${{ secrets.VERCEL_TOKEN }}
        env:
          VERCEL_ORG_ID: ${{ secrets.VERCEL_ORG_ID }}
          VERCEL_PROJECT_ID: ${{ secrets.VERCEL_PROJECT_ID }}

  deploy-production:
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Deploy to Vercel Production
        run: vercel --prod --token ${{ secrets.VERCEL_TOKEN }}
        env:
          VERCEL_ORG_ID: ${{ secrets.VERCEL_ORG_ID }}
          VERCEL_PROJECT_ID: ${{ secrets.VERCEL_PROJECT_ID }}

24.5 Docker (cho Self-hosting)

# Dockerfile cho Next.js
FROM node:20-alpine AS base

# Dependencies
FROM base AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci

# Build
FROM base AS builder
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
RUN npm run build

# Production image
FROM base AS runner
WORKDIR /app
ENV NODE_ENV production

# Next.js standalone output
COPY --from=builder /app/.next/standalone ./
COPY --from=builder /app/.next/static ./.next/static
COPY --from=builder /app/public ./public

EXPOSE 3000
ENV PORT 3000
CMD ["node", "server.js"]

# next.config.js — bật standalone output
const nextConfig = {
  output: 'standalone',
};

# docker-compose.yml
version: '3.8'
services:
  app:
    build: .
    ports:
      - "3000:3000"
    environment:
      - DATABASE_URL=${DATABASE_URL}
      - JWT_SECRET=${JWT_SECRET}
    depends_on:
      - postgres

  postgres:
    image: postgres:16-alpine
    volumes:
      - postgres_data:/var/lib/postgresql/data

      POSTGRES_DB: myapp
      POSTGRES_USER: user
      POSTGRES_PASSWORD: password

Bài tập 24.1: CI/CD Pipeline hoàn chỉnh

# Thiết lập pipeline cho dự án React:
# 1. Tạo repo GitHub
# 2. Thiết lập branch protection trên main:
#    - Require PR reviews
#    - Require status checks (test, build)
# 3. GitHub Actions workflow:
#    - Lint (ESLint)
#    - Type check (tsc --noEmit)
#    - Test (Vitest)
#    - Build
#    - Deploy preview (Vercel) khi có PR
#    - Deploy production khi merge vào main
# 4. Thêm secrets vào GitHub:
#    - VERCEL_TOKEN
#    - VERCEL_ORG_ID, VERCEL_PROJECT_ID
# 5. Tạo .env.example với tất cả env vars cần thiết

Câu hỏi ôn bài

1. Tại sao dùng npm ci trong CI/CD thay vì npm install?

  • A. npm ci nhanh hơn trong mọi trường hợp
  • B. npm ci luôn dùng chính xác package-lock.json — deterministic, không update packages, xóa node_modules trước
  • C. npm install không hoạt động trên Linux
  • D. npm ci ít tốn memory hơn

Đáp án: B — npm install: có thể update patch versions, tạo hoặc sửa package-lock.json. npm ci: install chính xác theo lock file, fail nếu lock file không khớp package.json. CI/CD cần reproducible builds.

2. Tại sao KHÔNG commit file .env vào git?

  • A. File .env quá lớn
  • B. .env chứa secrets (API keys, DB passwords) — commit vào git = lộ vĩnh viễn trong git history, ngay cả khi xóa sau
  • C. git không hỗ trợ .env files
  • D. .env chỉ hoạt động locally

Đáp án: B — Git history là vĩnh cửu. Một khi commit secrets, kẻ tấn công có thể đọc từ lịch sử ngay cả sau khi xóa file. Giải pháp: .gitignore, dùng secrets manager (GitHub Secrets, Vault), .env.example cho documentation.

3. Preview deployment trong Vercel/Netlify có mục đích gì?

  • A. Để luyện tập deploy
  • B. Mỗi PR tự động có URL riêng để review thay đổi trực quan trước khi merge vào production
  • C. Backup của production
  • D. Deploy nhanh hơn production

Đáp án: B — Preview URLs: team/stakeholders review UI trực tiếp mà không cần pull code về chạy local. Link tự động trong PR comments. Merge → production tự động cập nhật. Workflow hiệu quả, giảm "works on my machine".

4. Multi-stage Dockerfile giúp gì?

  • A. Build nhanh hơn trên mọi máy
  • B. Giảm kích thước image production — build tools (node_modules dev) không vào final image
  • C. Bảo mật secrets tốt hơn
  • D. Cho phép build nhiều service cùng lúc

Đáp án: B — Stage 1 (builder): install tất cả deps + build. Stage 2 (runner): chỉ copy output của build (standalone, static). Kết quả: image từ 1GB → 150MB. Nhỏ hơn = pull nhanh, ít surface tấn công.

5. LCP (Largest Contentful Paint) là gì và ảnh hưởng thế nào?

  • A. Lỗi lớn nhất trong code
  • B. Thời gian để phần tử lớn nhất (hero image, heading) hiển thị — ảnh hưởng trải nghiệm người dùng và SEO
  • C. Kích thước file JavaScript lớn nhất
  • D. Số lần render nhiều nhất

Đáp án: B — LCP < 2.5s = Good. LCP 2.5-4s = Needs Improvement. LCP > 4s = Poor. Google dùng Core Web Vitals (LCP, CLS, FID/INP) để rank search. Cải thiện: image optimization, preload hero image, SSG/SSR thay CSR.
